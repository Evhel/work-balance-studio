# Перенос сайта «ARV. Трудозатраты» на офисный сервер

Инструкция для системного администратора. Итог: сайт и база данных работают
внутри офисной сети, снаружи доступа нет (только через VPN), код лежит на GitHub.

## 1. Код на GitHub

В редакторе Lovable нажмите кнопку GitHub в правом верхнем углу и подключите
репозиторий. Дальше код синхронизируется в обе стороны: правки в Lovable
попадают в GitHub, правки в GitHub — обратно в Lovable.

Клонирование на сервере:

```sh
git clone <адрес-репозитория> arv
cd arv
```

## 2. База данных внутри сети

Сайту нужна база Supabase, развёрнутая на вашем сервере (self-hosted):

```sh
git clone --depth 1 https://github.com/supabase/supabase
cd supabase/docker
cp .env.example .env      # задайте пароли, JWT_SECRET, ANON_KEY, SERVICE_ROLE_KEY
docker compose up -d
```

После запуска проверьте и примените миграции из этого репозитория. Команда не
содержит паролей: SQL выполняется внутри локального контейнера PostgreSQL.

```powershell
powershell -ExecutionPolicy Bypass -File .\deploy\apply-migrations.ps1 -ValidateOnly
powershell -ExecutionPolicy Bypass -File .\deploy\apply-migrations.ps1
```

Создайте локальный `.env` приложения из ключей установленного Supabase. Для
проверки на самом сервере подходит адрес по умолчанию `127.0.0.1`; при открытии
доступа локальной сети передайте закреплённый IP сервера параметром
`-SupabaseUrl`.

```powershell
powershell -ExecutionPolicy Bypass -File .\deploy\configure-local-env.ps1
powershell -ExecutionPolicy Bypass -File .\deploy\configure-local-env.ps1 `
  -SupabaseUrl http://192.168.1.100:8000
```

Созданный `.env` содержит только адрес и публичный ключ и игнорируется Git.
Секретный `service_role` остаётся в защищённом серверном файле Supabase и
подставляется в процесс приложения только при запуске.

Для текущего офисного IP можно одной командой настроить адреса приложения и
Supabase и открыть в сеть только API-шлюз. PostgreSQL и его служебный порт
останутся привязаны к `127.0.0.1`:

```powershell
powershell -ExecutionPolicy Bypass -File .\deploy\configure-lan-access.ps1 `
  -LanAddress 192.168.88.12
```

Если IP компьютера изменится, выполните команду повторно с новым адресом, затем
заново соберите и запустите приложение. Постоянный адрес позднее настраивается
резервированием IP на роутере; эта операция не меняет данные сайта.

Соберите и запустите приложение. Скрипт запуска считывает `service_role`
непосредственно из защищённого файла и не печатает его в консоль.

```powershell
npm ci
npm run build
powershell -ExecutionPolicy Bypass -File .\deploy\start-local.ps1
powershell -ExecutionPolicy Bypass -File .\deploy\start-local.ps1 `
  -BindAddress 192.168.88.12
```

После изменений авторизации или ролей можно повторить изолированный тест прав.
Он создаёт временные локальные аккаунты сотрудника, офис-менеджера и модератора,
проверяет разрешённые и запрещённые операции и удаляет тестовые аккаунты в
блоке очистки.

```powershell
powershell -ExecutionPolicy Bypass -File .\deploy\test-account-permissions.ps1
```

После изменений общей рабочей базы можно повторить многопользовательский тест.
Он создаёт четыре временных локальных аккаунта, проверяет видимость изменений между
двумя независимыми сессиями, серверные запреты и приватность личных фильтров, а
затем удаляет все тестовые записи и аккаунты.

```powershell
powershell -ExecutionPolicy Bypass -File .\deploy\test-shared-data.ps1
```

Повторный запуск безопасен: применённые файлы пропускаются, а изменение уже
применённой миграции обнаруживается по SHA-256 независимо от переводов строк
Windows/Linux. `deploy/schema.sql` остаётся
снимком конечной структуры только для аварийного развёртывания чистой базы.

В настройках Supabase включите вход по email/паролю, автоподтверждение адресов
и отключите самостоятельную регистрацию — сотрудников заводит модератор или
офис-менеджер прямо на сайте.

## 3. Настройки сайта

```sh
cp .env.example .env
```

и подставьте адрес вашей базы и три ключа (anon, service role). Файл `.env`
в репозиторий не попадает.

## 4. Запуск сайта

Через Docker:

```sh
docker compose up -d --build
```

Или без Docker (нужен Node 22+ и bun):

```sh
bun install
NITRO_PRESET=node_server bun run build
PORT=3000 node .output/server/index.mjs
```

Сайт будет доступен по адресу `http://<ip-сервера>:3000`. Обычно перед ним
ставят nginx с доменным именем вида `arv.office.local` и сертификатом.

## 5. Доступ только из офиса

- Не настраивайте проброс портов `3000` и `8000` на роутере.
- Приложение и API привязываются к конкретному офисному IP командой из раздела
  2; служебные порты базы `5432` и `6543` доступны только на сервере.
- Если Windows блокирует подключение со второго компьютера, нужны два входящих
  разрешения TCP для портов `3000` и `8000`, ограниченные локальной подсетью.
  Это разовая настройка с правами администратора Windows.
- Доступ через VPN можно добавить позднее отдельным правилом, когда он
  понадобится.

## 6. Первый вход

Откройте сайт, страница `/auth` предложит создать первую учётную запись
модератора. Дальше модератор и офис-менеджер заводят сотрудников на странице
«Новый сотрудник».

## 7. Резервные копии

Установите локальные кнопки управления, автозапуск после входа в Windows и
еженедельную задачу резервного копирования:

```powershell
powershell -ExecutionPolicy Bypass -File .\deploy\install-local-operations.ps1
```

В `D:\prog\ARV-Server` появятся файлы `Start ARV.cmd`, `Stop ARV.cmd`,
`ARV Status.cmd` и `Backup ARV Now.cmd`. Сайт запускается автоматически после
входа владельца сервера в Windows. Ручной запуск остаётся доступен двойным
щелчком по `Start ARV.cmd`.

Задача `ARV Weekly Backup` запускается по воскресеньям в 03:00. Если компьютер
был выключен, Windows выполнит пропущенную задачу при следующей возможности.
Копии создаются в `D:\prog\ARV-Server\backups`, проверяются через `pg_restore`
и автоматически удаляются через 14 дней.

Ручная копия и полная тестовая распаковка в отдельную временную базу:

```powershell
powershell -ExecutionPolicy Bypass -File .\deploy\backup-database.ps1
powershell -ExecutionPolicy Bypass -File .\deploy\verify-backup.ps1 -FullRestoreTest
```

Тест восстановления не изменяет рабочую базу. Для реального восстановления
рабочей базы сначала остановите приложение и сохраните текущую копию; не
выполняйте восстановление поверх рабочей базы без дополнительной проверки.

Копии на том же диске защищают от случайной порчи данных, но не от поломки или
потери всего диска D. Для защиты от отказа диска позднее понадобится второй
локальный носитель.

## 8. Обновление из GitHub и Lovable

Сначала дважды щёлкните `D:\prog\ARV-Server\Check ARV Updates.cmd`. Эта
проверка только загружает список новых коммитов и файлов, но не меняет сайт.

После проверки запустите `D:\prog\ARV-Server\Update ARV.cmd`. Сценарий:

1. отказывается работать при незаписанных локальных изменениях или расхождении
   истории Git;
2. создаёт и проверяет свежую резервную копию базы;
3. принимает только fast-forward изменения ветки `origin/main`;
4. ненадолго останавливает приложение, но не базу;
5. устанавливает точные зависимости и создаёт новую production-сборку;
6. сначала проверяет миграции базы без изменений, затем применяет только ещё не
   применённые миграции;
7. запускает сайт и проверяет HTTP 200.

Предыдущая рабочая сборка сохраняется в `D:\prog\ARV-Server\releases`. Если
новая сборка или запуск завершаются ошибкой, сценарий возвращает предыдущую
сборку и пытается снова запустить сайт. База не очищается и не создаётся заново.
При ошибке миграции не повторяйте обновление вслепую: сохраните текст ошибки и
передайте его на проверку.
